OAuth позволяет Cyberstrike аутентифицироваться на удалённом MCP-сервере без хранения долгоживущих учётных данных. Cyberstrike обнаруживает конечные точки OAuth сервера автоматически — вы указываете данные клиента только когда сервер их требует.

## Схема конфигурации

OAuth — необязательный блок на **удалённом** MCP-сервере. Полная схема содержит всего три необязательных поля:

```json title="~/.config/cyberstrike/cyberstrike.json"
{
  "mcp": {
    "my-server": {
      "type": "remote",
      "url": "https://mcp.example.com/mcp",
      "oauth": {
        "clientId": "{env:OAUTH_CLIENT_ID}",
        "clientSecret": "{env:OAUTH_CLIENT_SECRET}",
        "scope": "read write"
      }
    }
  }
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `clientId` | string | Необязательно. Если не указан, выполняется попытка **динамической регистрации клиента (RFC 7591)**. |
| `clientSecret` | string | Необязательно. Только если сервер авторизации требует конфиденциального клиента. |
| `scope` | string | Необязательно. Запрашиваемые области доступа при авторизации. |

<Aside variant="caution">
  URL авторизации и токена **не** настраиваются здесь — Cyberstrike обнаруживает их из метаданных OAuth сервера. Поля `authorizationUrl`, `tokenUrl`, `pkce`, `deviceAuthorizationUrl`, `grantType` и `callbackPort`/`callbackPath` **не существуют** в схеме (только `clientId`, `clientSecret`, `scope`).
</Aside>

## Как это работает

1. Cyberstrike определяет, что удалённый сервер требует OAuth (из его метаданных).
2. Если `clientId` не установлен, выполняется динамическая регистрация клиента (RFC 7591).
3. Открывается ваш браузер на URL авторизации; вы входите и предоставляете доступ.
4. Код авторизации обменивается на токены через локальный callback, обрабатываемый внутренне.
5. Токены сохраняются Cyberstrike и обновляются автоматически при истечении срока.

Установите `"oauth": false` на сервере, чтобы полностью отключить автообнаружение OAuth.

## Авторизация сервера

Запустите авторизацию из CLI:

```bash
cyberstrike mcp auth <name>       # авторизовать сервер
cyberstrike mcp auth list         # список серверов с OAuth-авторизацией
cyberstrike mcp logout <name>     # удалить сохранённые учётные данные OAuth
```

Cyberstrike также автоматически запрашивает авторизацию при первом использовании OAuth-защищённого сервера в сессии. Обновление токенов происходит автоматически — команды ручного обновления нет.

## Пример: сервер с областями доступа

```json
{
  "mcp": {
    "example-mcp": {
      "type": "remote",
      "url": "https://mcp.example.com/mcp",
      "oauth": {
        "scope": "openid profile email"
      }
    }
  }
}
```

Без `clientId` Cyberstrike регистрирует клиент динамически, затем авторизуется с запрошенными областями.

## Замечания по безопасности

- Ссылайтесь на секреты через `{env:VAR}` — никогда не коммитьте `clientSecret` в систему контроля версий.
- Запрашивайте минимальные области доступа, необходимые серверу.
- Удаляйте учётные данные командой `cyberstrike mcp logout <name>`, когда они больше не нужны.

## Устранение неполадок

- **Ошибка авторизации** — убедитесь, что URL сервера доступен, и (если сервер требует конфиденциального клиента) что `clientId`/`clientSecret` верны.
- **Повторные запросы авторизации** — сохранённый токен мог быть отозван на стороне сервера; выполните `cyberstrike mcp auth <name>` снова.
- **Таймаут callback** — убедитесь, что браузер завершил вход и локальный файрвол не блокирует loopback callback.
- Проверьте подключение сервера с помощью `cyberstrike mcp debug <name>`.
