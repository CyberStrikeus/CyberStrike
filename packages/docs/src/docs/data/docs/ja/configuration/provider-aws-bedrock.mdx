AWS Bedrockを使用すると、自身のAWSアカウントでCyberStrikeを実行できます。データは自社インフラストラクチャ内に留まり、IAMベースのアクセス制御が利用でき、VPCエンドポイントでプライベートネットワークアクセスが可能です。

CyberStrikeは標準的なAWS資格情報プロバイダーチェーン(`@aws-sdk/credential-providers`)を使用するため、既にAWS CLIやSDKを使用している場合は、既存の資格情報がそのまま動作します。

## 前提条件

開始する前に、AWSアカウントでBedrockモデルへのアクセス権があることを確認してください:

<Steps>
1. **AWSコンソール**を開き、**Amazon Bedrock**に移動
2. 左サイドバーの**モデルアクセス**をクリック
3. 使用したいClaudeモデルへのアクセスをリクエスト
4. 承認を待つ(ほとんどのモデルでは通常即座に承認)
</Steps>

## クイックスタート

最速の開始方法はセットアップに依存します:

```bash
# AWS CLIが既に設定されている場合
cyberstrike

# 名前付きプロファイルがある場合
AWS_PROFILE=my-profile cyberstrike

# アクセスキーがある場合
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... cyberstrike

# IAMロールがアタッチされたEC2上 -- そのまま実行
cyberstrike
```

CyberStrikeはAWS資格情報を自動検出します。Bedrockの資格情報が見つかると、プロバイダーがモデルセレクターに自動的に表示されます。

## 認証方法

CyberStrikeはAWS Bedrockでの認証に9つの異なる方法をサポートしています。ここでは最もシンプルなものから最も高度なものまで順に紹介します。

---

### 1. AWSアクセスキー

最も直接的な方法です。アクセスキーとシークレットを環境変数として設定します:

```bash
export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE"
export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
export AWS_REGION="us-east-1"

cyberstrike
```

単一セッション用にインラインで渡すこともできます:

```bash
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... AWS_REGION=us-east-1 cyberstrike
```

<Aside variant="caution">
  アクセスキーは長期間有効な資格情報です。本番環境では、代わりにIAMロール、SSO、または一時的な資格情報を使用してください。
</Aside>

---

### 2. AWSプロファイル

`~/.aws/credentials`と`~/.aws/config`にプロファイルが設定されている場合、選択できます:

```bash
# 名前付きプロファイルを使用
AWS_PROFILE=my-profile cyberstrike
```

またはプロジェクトの`cyberstrike.json`でプロファイルを設定:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "profile": "my-profile",
        "region": "us-east-1"
      }
    }
  }
}
```

<Aside variant="tip">
  `cyberstrike.json`と`AWS_PROFILE`環境変数の両方が設定されている場合、設定ファイルが優先されます。
</Aside>

---

### 3. SSO / IAM Identity Center

組織がAWS IAM Identity Center(旧AWS SSO)を使用している場合、`~/.aws/config`でSSOプロファイルを設定します:

```ini title="~/.aws/config"
[profile my-sso]
sso_session = my-org
sso_account_id = 123456789012
sso_role_name = BedrockAccess
region = us-east-1

[sso-session my-org]
sso_start_url = https://my-org.awsapps.com/start
sso_region = us-east-1
```

ログインしてCyberStrikeを実行:

```bash
aws sso login --profile my-sso
AWS_PROFILE=my-sso cyberstrike
```

---

### 4. STS AssumeRole (ロールチェーン)

別のAWSアカウント(または同じアカウント内のより高い権限のロール)のロールを引き受ける必要がある場合、`~/.aws/config`でロールチェーンを設定します:

```ini title="~/.aws/config"
[profile base-account]
aws_access_key_id = AKIA...
aws_secret_access_key = ...

[profile bedrock-role]
role_arn = arn:aws:iam::987654321098:role/BedrockAccessRole
source_profile = base-account
region = us-east-1
```

ロールプロファイルを使用:

```bash
AWS_PROFILE=bedrock-role cyberstrike
```

これはAWS資格情報プロバイダーチェーンによって自動的に処理されます -- CyberStrikeに特別な設定は必要ありません。

---

### 5. Webアイデンティティトークン(OIDC)

**EKS(Kubernetes)**、**GitHub Actions**、その他のOIDCフェデレーション環境で実行されるワークロードの場合、トークンファイルパスを設定します:

```bash
export AWS_WEB_IDENTITY_TOKEN_FILE="/var/run/secrets/eks.amazonaws.com/serviceaccount/token"
export AWS_ROLE_ARN="arn:aws:iam::123456789012:role/my-eks-role"

cyberstrike
```

IRSA(IAM Roles for Service Accounts)を使用するEKSでは、これらの環境変数はKubernetesによって自動的に設定されます。

---

### 6. コンテナ資格情報(ECS / Fargate)

**ECS**または**Fargate**タスク内で実行する場合、AWSはメタデータエンドポイントを通じて自動的に資格情報を注入します。CyberStrikeはこれらの環境変数を検出します:

- `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`
- `AWS_CONTAINER_CREDENTIALS_FULL_URI`

設定は不要です -- タスクのIAMロールにBedrock権限があることを確認して実行:

```bash
cyberstrike
```

---

### 7. EC2インスタンスメタデータ(IMDS)

IAMロールがアタッチされた**EC2インスタンス**では、インスタンスメタデータサービスから資格情報が自動的に取得されます。環境変数や設定ファイルは不要です:

```bash
# IAMロール付きEC2インスタンス上 -- そのまま実行
cyberstrike
```

インスタンスのIAMロールに以下の[IAM権限](#iam-permissions)セクションで説明するBedrock権限が含まれていることを確認してください。

<Aside variant="info">
  標準の資格情報チェーンが失敗した場合、CyberStrikeは最後の手段としてIMDSに自動的にフォールバックします。
</Aside>

---

### 8. ベアラートークン

ベアラートークンで認証できます。環境変数で設定:

```bash
export AWS_BEARER_TOKEN_BEDROCK="your-bearer-token"
cyberstrike
```

またはTUIを通じて保存 -- `/connect`を実行し、**Amazon Bedrock**を選択して、プロンプトが表示されたらベアラートークンを貼り付けます。トークンが保存されるため、毎回設定する必要はありません。

<Aside variant="tip">
  ベアラートークンは**最高優先度**です -- 設定すると、AWS資格情報チェーン全体(プロファイル、アクセスキー、IAMロールなど)がバイパスされます。
</Aside>

---

### 9. カスタム資格情報プロセス

一時的なAWS資格情報を生成するカスタムツール(企業の資格情報自動販売機など)がある場合、`~/.aws/config`で設定します:

```ini title="~/.aws/config"
[profile custom-creds]
credential_process = /usr/local/bin/my-credential-tool --format json
region = us-east-1
```

プログラムはこの形式のJSONを返す必要があります:

```json
{
  "Version": 1,
  "AccessKeyId": "AKIA...",
  "SecretAccessKey": "...",
  "SessionToken": "...",
  "Expiration": "2025-12-31T23:59:59Z"
}
```

プロファイルを使用:

```bash
AWS_PROFILE=custom-creds cyberstrike
```

## 認証の優先順位

複数の資格情報が利用可能な場合、CyberStrikeはこの優先順位を使用します:

| 優先度 | 方法 | ソース |
|----------|--------|--------|
| 1 (最高) | ベアラートークン | `AWS_BEARER_TOKEN_BEDROCK`環境変数またはTUIの`/connect` |
| 2 | AWS資格情報チェーン | `fromNodeProviderChain`が標準AWS SDK順序で解決: 環境変数 --> プロファイル --> SSO --> Webアイデンティティ --> ECSコンテナ --> EC2 IMDS |

## IAM権限

どの認証方法を使用する場合でも、IAMアイデンティティにはこれらの権限が必要です:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "arn:aws:bedrock:*::foundation-model/anthropic.*"
    }
  ]
}
```

<Aside variant="tip">
  特定のモデルのみにアクセスを制限したい場合は、`anthropic.*`を特定のモデルARNに置き換えてください。
</Aside>

## リージョン設定

CyberStrikeはこの順序でAWSリージョンを解決します:

| 優先度 | ソース | 例 |
|----------|--------|---------|
| 1 (最高) | `cyberstrike.json`設定 | `provider.amazon-bedrock.options.region` |
| 2 | 環境変数 | `AWS_REGION=eu-west-1` |
| 3 (デフォルト) | ハードコードされたフォールバック | `us-east-1` |

設定ファイルでリージョンを設定:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "eu-west-1"
      }
    }
  }
}
```

または環境変数で:

```bash
export AWS_REGION="eu-west-1"
```

## クロスリージョン推論

CyberStrikeはクロスリージョン推論プロファイルのプレフィックスを自動的に処理します。設定されたリージョンに基づいて、モデルIDに正しいプレフィックスが追加されます:

| リージョン | プレフィックス | 例 |
|--------|--------|---------|
| USリージョン (us-east-1, us-west-2, ...) | `us.` | `us.anthropic.claude-sonnet-4-20250514-v1:0` |
| EUリージョン (eu-west-1, eu-central-1, ...) | `eu.` | `eu.anthropic.claude-sonnet-4-20250514-v1:0` |
| 東京 (ap-northeast-1) | `jp.` | `jp.anthropic.claude-sonnet-4-20250514-v1:0` |
| オーストラリア (ap-southeast-2, ap-southeast-4) | `au.` | `au.anthropic.claude-sonnet-4-20250514-v1:0` |
| その他のAPACリージョン | `apac.` | `apac.anthropic.claude-sonnet-4-20250514-v1:0` |
| グローバル | `global.` | `global.anthropic.claude-sonnet-4-20250514-v1:0` |

これは自動的に行われます -- プレフィックスを自分で追加する必要はありません。モデルIDに既にプレフィックスがある場合(例: モデルセレクターからの場合)、二重プレフィックスは付きません。

## VPCエンドポイント

プライベートネットワークアクセス(インターネットトラフィックなし)には、VPCエンドポイントを設定:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1",
        "endpoint": "https://bedrock-runtime.us-east-1.vpce-xxxxx.amazonaws.com"
      }
    }
  }
}
```

## 使い方

認証が設定されたら、TUIの`/models`でBedrockモデルを選択するか、設定でデフォルトを指定:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1"
      }
    }
  },
  "model": "amazon-bedrock/anthropic.claude-sonnet-4-20250514-v1:0"
}
```

セッション中にモデルを切り替えるには、`/model`スラッシュコマンドを使用してください。

## トラブルシューティング

### 「Access Denied」エラー

- AWS Bedrockコンソールでモデルアクセスが有効になっていることを確認
- IAMポリシーに`bedrock:InvokeModel`と`bedrock:InvokeModelWithResponseStream`が含まれていることを確認
- 正しいリージョンを使用していることを確認

### 「Model not found」エラー

- モデルIDが正しいことを確認
- モデルがリージョンで利用可能か確認
- 別のリージョンを試すか、クロスリージョン推論を有効にする

### 「ThrottlingException」エラー

- AWSコンソールでサービス制限の引き上げをリクエスト
- クロスリージョン推論でリージョン間の負荷を分散できます
- 安定したスループットには、AWS Bedrockプロビジョンドキャパシティを検討

### Bedrockプロバイダーが表示されない

CyberStrikeは有効な資格情報を検出した場合にのみBedrockプロバイダーを表示します。表示されない場合:

1. AWS CLIで資格情報が動作することを確認: `aws bedrock list-foundation-models --region us-east-1`
2. 少なくとも1つの認証方法が設定されていることを確認(環境変数、プロファイル、設定など)
3. `cyberstrike.json`の`disabled_providers`にプロバイダーがリストされていないことを確認
