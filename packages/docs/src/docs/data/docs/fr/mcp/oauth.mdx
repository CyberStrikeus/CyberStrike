OAuth permet a Cyberstrike de s'authentifier aupres d'un serveur MCP distant sans stocker d'identifiants a longue duree de vie. Cyberstrike decouvre automatiquement les endpoints OAuth du serveur — vous ne fournissez les details du client que lorsque le serveur les exige.

<img src="/docs/images/diagrams/oauth-flow.svg" alt="Flux OAuth MCP : detection OAuth, enregistrement dynamique de client si pas de clientId, autorisation navigateur, echange de code contre des tokens, tokens stockes et rafraichis automatiquement" className="my-6 mx-auto max-w-xs" />

## Schema de configuration

OAuth est un bloc optionnel sur un serveur MCP **distant**. Le schema complet ne comprend que trois champs optionnels :

```json title="~/.config/cyberstrike/cyberstrike.json"
{
  "mcp": {
    "my-server": {
      "type": "remote",
      "url": "https://mcp.example.com/mcp",
      "oauth": {
        "clientId": "{env:OAUTH_CLIENT_ID}",
        "clientSecret": "{env:OAUTH_CLIENT_SECRET}",
        "scope": "read write"
      }
    }
  }
}
```

| Champ | Type | Description |
|-------|------|-------------|
| `clientId` | string | Optionnel. Si omis, l'**enregistrement dynamique de client (RFC 7591)** est tente. |
| `clientSecret` | string | Optionnel. Uniquement si le serveur d'autorisation exige un client confidentiel. |
| `scope` | string | Optionnel. Portees a demander lors de l'autorisation. |

<Aside variant="caution">
  Les URLs d'autorisation et de token ne sont **pas** configurees ici — Cyberstrike les decouvre depuis les metadonnees OAuth du serveur. Les champs comme `authorizationUrl`, `tokenUrl`, `pkce`, `deviceAuthorizationUrl`, `grantType` et `callbackPort`/`callbackPath` n'existent **pas** dans le schema (`clientId`, `clientSecret`, `scope` uniquement).
</Aside>

## Fonctionnement

1. Cyberstrike detecte que le serveur distant necessite OAuth (depuis ses metadonnees).
2. Si aucun `clientId` n'est defini, il enregistre un client dynamiquement (RFC 7591).
3. Il ouvre votre navigateur vers l'URL d'autorisation ; vous vous connectez et accordez l'acces.
4. Le code d'autorisation est echange contre des tokens sur un callback local gere en interne.
5. Les tokens sont stockes par Cyberstrike et rafraichis automatiquement a leur expiration.

Definissez `"oauth": false` sur le serveur pour desactiver completement la detection automatique OAuth.

## Autoriser un serveur

Declenchez l'autorisation depuis la CLI :

```bash
cyberstrike mcp auth <name>       # autoriser un serveur
cyberstrike mcp auth list         # lister les serveurs autorises par OAuth
cyberstrike mcp logout <name>     # supprimer les identifiants OAuth stockes
```

Cyberstrike demande egalement l'autorisation automatiquement la premiere fois qu'un serveur protege par OAuth est utilise dans une session. Le rafraichissement des tokens est automatique — il n'y a pas de commande de rafraichissement manuelle.

## Exemple : un serveur avec portees

```json
{
  "mcp": {
    "example-mcp": {
      "type": "remote",
      "url": "https://mcp.example.com/mcp",
      "oauth": {
        "scope": "openid profile email"
      }
    }
  }
}
```

Sans `clientId`, Cyberstrike enregistre un client dynamiquement, puis autorise avec les portees demandees.

## Notes de securite

- Referencez les secrets avec `{env:VAR}` — ne commitez jamais un `clientSecret` dans le controle de version.
- Demandez les portees minimales dont le serveur a besoin.
- Supprimez les identifiants avec `cyberstrike mcp logout <name>` lorsqu'ils ne sont plus necessaires.

## Depannage

- **Echec d'autorisation** — confirmez que l'URL du serveur est joignable et (si le serveur necessite un client confidentiel) que `clientId`/`clientSecret` sont corrects.
- **Demandes d'authentification repetees** — le token stocke a peut-etre ete revoque cote serveur ; executez `cyberstrike mcp auth <name>` a nouveau.
- **Timeout du callback** — assurez-vous que votre navigateur a termine la connexion et qu'un pare-feu local ne bloque pas le callback loopback.
- Inspectez la connexion d'un serveur avec `cyberstrike mcp debug <name>`.
