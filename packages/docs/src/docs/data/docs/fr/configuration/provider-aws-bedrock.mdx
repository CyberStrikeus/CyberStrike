AWS Bedrock vous permet d'exécuter CyberStrike via votre propre compte AWS. Vos données restent dans votre infrastructure, vous bénéficiez du contrôle d'accès basé sur IAM, et vous pouvez utiliser des points de terminaison VPC pour l'accès réseau privé.

CyberStrike utilise la chaîne standard de fournisseur d'identifiants AWS (`@aws-sdk/credential-providers`), donc si vous utilisez déjà l'AWS CLI ou les SDK, vos identifiants existants fonctionneront.

## Prérequis

Avant de commencer, assurez-vous d'avoir accès aux modèles Bedrock dans votre compte AWS :

<Steps>
1. Ouvrez la **Console AWS** et accédez à **Amazon Bedrock**
2. Cliquez sur **Model access** dans la barre latérale gauche
3. Demandez l'accès aux modèles Claude que vous souhaitez utiliser
4. Attendez l'approbation (généralement instantanée pour la plupart des modèles)
</Steps>

## Démarrage rapide

La façon la plus rapide de commencer dépend de votre configuration :

```bash
# Si vous avez déjà l'AWS CLI configurée
cyberstrike

# Si vous avez un profil nommé
AWS_PROFILE=my-profile cyberstrike

# Si vous avez des clés d'accès
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... cyberstrike

# Sur EC2 avec un rôle IAM attaché — lancez simplement
cyberstrike
```

CyberStrike détecte automatiquement vos identifiants AWS. Si des identifiants Bedrock sont trouvés, le fournisseur apparaît automatiquement dans le sélecteur de modèle.

## Méthodes d'authentification

CyberStrike prend en charge 9 façons différentes de s'authentifier avec AWS Bedrock. Elles sont listées ici de la plus simple à la plus avancée.

---

### 1. Clés d'accès AWS

La méthode la plus directe. Définissez votre clé d'accès et votre secret comme variables d'environnement :

```bash
export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE"
export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
export AWS_REGION="us-east-1"

cyberstrike
```

Vous pouvez aussi les passer en ligne pour une seule session :

```bash
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... AWS_REGION=us-east-1 cyberstrike
```

<Aside variant="caution">
  Les clés d'accès sont des identifiants à longue durée de vie. Pour un usage en production, préférez les rôles IAM, le SSO ou les identifiants temporaires.
</Aside>

---

### 2. Profils AWS

Si vous avez des profils configurés dans `~/.aws/credentials` et `~/.aws/config`, vous pouvez en sélectionner un :

```bash
# Utiliser un profil nommé
AWS_PROFILE=my-profile cyberstrike
```

Ou définissez le profil dans le `cyberstrike.json` de votre projet :

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "profile": "my-profile",
        "region": "us-east-1"
      }
    }
  }
}
```

<Aside variant="tip">
  Lorsque `cyberstrike.json` et la variable d'environnement `AWS_PROFILE` sont tous deux définis, le fichier de configuration a la priorité.
</Aside>

---

### 3. SSO / IAM Identity Center

Si votre organisation utilise AWS IAM Identity Center (anciennement AWS SSO), configurez un profil SSO dans `~/.aws/config` :

```ini title="~/.aws/config"
[profile my-sso]
sso_session = my-org
sso_account_id = 123456789012
sso_role_name = BedrockAccess
region = us-east-1

[sso-session my-org]
sso_start_url = https://my-org.awsapps.com/start
sso_region = us-east-1
```

Puis connectez-vous et lancez CyberStrike :

```bash
aws sso login --profile my-sso
AWS_PROFILE=my-sso cyberstrike
```

---

### 4. STS AssumeRole (chaînage de rôles)

Si vous devez assumer un rôle dans un autre compte AWS (ou un rôle plus privilégié dans le même compte), configurez le chaînage de rôles dans `~/.aws/config` :

```ini title="~/.aws/config"
[profile base-account]
aws_access_key_id = AKIA...
aws_secret_access_key = ...

[profile bedrock-role]
role_arn = arn:aws:iam::987654321098:role/BedrockAccessRole
source_profile = base-account
region = us-east-1
```

Puis utilisez le profil de rôle :

```bash
AWS_PROFILE=bedrock-role cyberstrike
```

Ceci est géré automatiquement par la chaîne de fournisseur d'identifiants AWS — CyberStrike n'a besoin d'aucune configuration spéciale.

---

### 5. Jeton d'identité web (OIDC)

Pour les charges de travail exécutées sur **EKS (Kubernetes)**, **GitHub Actions**, ou d'autres environnements fédérés OIDC, définissez le chemin du fichier de jeton :

```bash
export AWS_WEB_IDENTITY_TOKEN_FILE="/var/run/secrets/eks.amazonaws.com/serviceaccount/token"
export AWS_ROLE_ARN="arn:aws:iam::123456789012:role/my-eks-role"

cyberstrike
```

Sur EKS avec IRSA (rôles IAM pour les comptes de service), ces variables d'environnement sont définies automatiquement par Kubernetes.

---

### 6. Identifiants de conteneur (ECS / Fargate)

Lors de l'exécution à l'intérieur de tâches **ECS** ou **Fargate**, AWS injecte les identifiants automatiquement via un point de terminaison de métadonnées. CyberStrike détecte ces variables d'environnement :

- `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`
- `AWS_CONTAINER_CREDENTIALS_FULL_URI`

Aucune configuration nécessaire — assurez-vous simplement que le rôle IAM de la tâche a les permissions Bedrock et lancez :

```bash
cyberstrike
```

---

### 7. Métadonnées d'instance EC2 (IMDS)

Sur les **instances EC2** avec un rôle IAM attaché, les identifiants sont récupérés automatiquement depuis le service de métadonnées de l'instance. Aucune variable d'environnement ni fichier de configuration nécessaire :

```bash
# Sur une instance EC2 avec un rôle IAM — lancez simplement
cyberstrike
```

Assurez-vous que le rôle IAM de l'instance inclut les permissions Bedrock décrites dans la section [Permissions IAM](#permissions-iam) ci-dessous.

<Aside variant="info">
  Si la chaîne standard d'identifiants échoue, CyberStrike se rabat automatiquement sur IMDS en dernier recours.
</Aside>

---

### 8. Jeton porteur (Bearer Token)

Vous pouvez vous authentifier avec un jeton porteur. Définissez-le via une variable d'environnement :

```bash
export AWS_BEARER_TOKEN_BEDROCK="your-bearer-token"
cyberstrike
```

Ou enregistrez-le via le TUI — exécutez `/connect`, sélectionnez **Amazon Bedrock**, et collez votre jeton porteur lorsqu'il est demandé. Cela sauvegarde le jeton pour ne pas avoir à le redéfinir à chaque fois.

<Aside variant="tip">
  Le jeton porteur a la **priorité la plus haute** — lorsqu'il est défini, il contourne toute la chaîne d'identifiants AWS (profils, clés d'accès, rôles IAM, etc.).
</Aside>

---

### 9. Processus d'identifiants personnalisé

Si vous avez un outil personnalisé qui génère des identifiants AWS temporaires (comme un distributeur d'identifiants d'entreprise), configurez-le dans `~/.aws/config` :

```ini title="~/.aws/config"
[profile custom-creds]
credential_process = /usr/local/bin/my-credential-tool --format json
region = us-east-1
```

Le programme doit retourner du JSON dans ce format :

```json
{
  "Version": 1,
  "AccessKeyId": "AKIA...",
  "SecretAccessKey": "...",
  "SessionToken": "...",
  "Expiration": "2025-12-31T23:59:59Z"
}
```

Puis utilisez le profil :

```bash
AWS_PROFILE=custom-creds cyberstrike
```

---

## Priorité d'authentification

Lorsque plusieurs identifiants sont disponibles, CyberStrike utilise cet ordre de priorité :

| Priorité | Méthode | Source |
|----------|--------|--------|
| 1 (plus haute) | Jeton porteur | Variable d'env `AWS_BEARER_TOKEN_BEDROCK` ou `/connect` dans le TUI |
| 2 | Chaîne d'identifiants AWS | `fromNodeProviderChain` résout dans l'ordre standard du SDK AWS : vars d'env → profil → SSO → identité web → conteneur ECS → IMDS EC2 |

## Permissions IAM

Quelle que soit la méthode d'authentification utilisée, l'identité IAM a besoin de ces permissions :

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "arn:aws:bedrock:*::foundation-model/anthropic.*"
    }
  ]
}
```

<Aside variant="tip">
  Remplacez `anthropic.*` par un ARN de modèle spécifique si vous souhaitez restreindre l'accès à certains modèles uniquement.
</Aside>

## Configuration de la région

CyberStrike résout la région AWS dans cet ordre :

| Priorité | Source | Exemple |
|----------|--------|---------|
| 1 (plus haute) | Configuration `cyberstrike.json` | `provider.amazon-bedrock.options.region` |
| 2 | Variable d'environnement | `AWS_REGION=eu-west-1` |
| 3 (par défaut) | Valeur par défaut codée en dur | `us-east-1` |

Définissez la région dans votre fichier de configuration :

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "eu-west-1"
      }
    }
  }
}
```

Ou via une variable d'environnement :

```bash
export AWS_REGION="eu-west-1"
```

## Inférence inter-régions

CyberStrike gère automatiquement les préfixes de profil d'inférence inter-régions. En fonction de votre région configurée, le préfixe correct est ajouté aux ID de modèle :

| Région | Préfixe | Exemple |
|--------|--------|---------|
| Régions US (us-east-1, us-west-2, ...) | `us.` | `us.anthropic.claude-sonnet-4-20250514-v1:0` |
| Régions EU (eu-west-1, eu-central-1, ...) | `eu.` | `eu.anthropic.claude-sonnet-4-20250514-v1:0` |
| Tokyo (ap-northeast-1) | `jp.` | `jp.anthropic.claude-sonnet-4-20250514-v1:0` |
| Australie (ap-southeast-2, ap-southeast-4) | `au.` | `au.anthropic.claude-sonnet-4-20250514-v1:0` |
| Autres régions APAC | `apac.` | `apac.anthropic.claude-sonnet-4-20250514-v1:0` |
| Global | `global.` | `global.anthropic.claude-sonnet-4-20250514-v1:0` |

C'est automatique — vous n'avez pas besoin d'ajouter ces préfixes vous-même. Si un ID de modèle a déjà un préfixe (ex. depuis le sélecteur de modèle), il ne sera pas doublement préfixé.

## Point de terminaison VPC

Pour l'accès réseau privé (pas de trafic internet), configurez un point de terminaison VPC :

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1",
        "endpoint": "https://bedrock-runtime.us-east-1.vpce-xxxxx.amazonaws.com"
      }
    }
  }
}
```

## Utilisation

Une fois l'authentification configurée, sélectionnez un modèle Bedrock via `/models` dans le TUI, ou définissez un modèle par défaut dans la configuration :

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1"
      }
    }
  },
  "model": "amazon-bedrock/anthropic.claude-sonnet-4-20250514-v1:0"
}
```

Pour changer de modèle pendant une session, utilisez la commande slash `/model`.

## Dépannage

### Erreur "Access Denied"

- Vérifiez que l'accès au modèle est activé dans la console AWS Bedrock
- Vérifiez que votre politique IAM inclut `bedrock:InvokeModel` et `bedrock:InvokeModelWithResponseStream`
- Confirmez que vous utilisez la bonne région

### Erreur "Model not found"

- Vérifiez que l'ID du modèle est correct
- Vérifiez si le modèle est disponible dans votre région
- Essayez une autre région ou activez l'inférence inter-régions

### Erreur "ThrottlingException"

- Demandez une augmentation de la limite de service via la console AWS
- L'inférence inter-régions peut aider à répartir la charge entre les régions
- Pour un débit constant, envisagez la capacité provisionnée AWS Bedrock

### Le fournisseur Bedrock n'apparaît pas

CyberStrike n'affiche le fournisseur Bedrock que lorsqu'il détecte des identifiants valides. S'il n'apparaît pas :

1. Vérifiez que vos identifiants fonctionnent avec l'AWS CLI : `aws bedrock list-foundation-models --region us-east-1`
2. Vérifiez qu'au moins une méthode d'authentification est configurée (vars d'env, profil, config, etc.)
3. Assurez-vous que le fournisseur n'est pas listé dans `disabled_providers` de votre `cyberstrike.json`
