AWS Bedrock ermoeglicht es Ihnen, CyberStrike ueber Ihr eigenes AWS-Konto auszufuehren. Ihre Daten bleiben in Ihrer Infrastruktur, Sie erhalten IAM-basierte Zugriffskontrolle und koennen VPC-Endpunkte fuer privaten Netzwerkzugriff verwenden.

CyberStrike verwendet die Standard-AWS-Credential-Provider-Kette (`@aws-sdk/credential-providers`), wenn Sie also bereits die AWS CLI oder SDKs verwenden, funktionieren Ihre bestehenden Anmeldedaten.

## Voraussetzungen

Bevor Sie beginnen, stellen Sie sicher, dass Sie Zugriff auf Bedrock-Modelle in Ihrem AWS-Konto haben:

<Steps>
1. Oeffnen Sie die **AWS-Konsole** und navigieren Sie zu **Amazon Bedrock**
2. Klicken Sie in der linken Seitenleiste auf **Modellzugriff**
3. Beantragen Sie Zugriff auf die Claude-Modelle, die Sie verwenden moechten
4. Warten Sie auf die Genehmigung (fuer die meisten Modelle normalerweise sofort)
</Steps>

## Schnellstart

Der schnellste Einstieg haengt von Ihrem Setup ab:

```bash
# Wenn Sie die AWS CLI bereits konfiguriert haben
cyberstrike

# Wenn Sie ein benanntes Profil haben
AWS_PROFILE=my-profile cyberstrike

# Wenn Sie Zugriffsschluessel haben
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... cyberstrike

# Auf EC2 mit angehaengter IAM-Rolle — einfach ausfuehren
cyberstrike
```

CyberStrike erkennt Ihre AWS-Anmeldedaten automatisch. Wenn Bedrock-Anmeldedaten gefunden werden, erscheint der Anbieter automatisch in der Modellauswahl.

## Authentifizierungsmethoden

CyberStrike unterstuetzt 9 verschiedene Wege zur Authentifizierung mit AWS Bedrock. Sie sind hier vom einfachsten bis zum fortgeschrittensten aufgefuehrt.

---

### 1. AWS-Zugriffsschluessel

Die einfachste Methode. Setzen Sie Ihren Zugriffsschluessel und Geheimschluessel als Umgebungsvariablen:

```bash
export AWS_ACCESS_KEY_ID="AKIAIOSFODNN7EXAMPLE"
export AWS_SECRET_ACCESS_KEY="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
export AWS_REGION="us-east-1"

cyberstrike
```

Sie koennen sie auch inline fuer eine einzelne Sitzung uebergeben:

```bash
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... AWS_REGION=us-east-1 cyberstrike
```

<Aside variant="caution">
  Zugriffsschluessel sind langlebige Anmeldedaten. Fuer den Produktiveinsatz bevorzugen Sie IAM-Rollen, SSO oder temporaere Anmeldedaten.
</Aside>

---

### 2. AWS-Profile

Wenn Sie Profile in `~/.aws/credentials` und `~/.aws/config` konfiguriert haben, koennen Sie eines auswaehlen:

```bash
# Ein benanntes Profil verwenden
AWS_PROFILE=my-profile cyberstrike
```

Oder setzen Sie das Profil in der `cyberstrike.json` Ihres Projekts:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "profile": "my-profile",
        "region": "us-east-1"
      }
    }
  }
}
```

<Aside variant="tip">
  Wenn sowohl `cyberstrike.json` als auch die Umgebungsvariable `AWS_PROFILE` gesetzt sind, hat die Konfigurationsdatei Vorrang.
</Aside>

---

### 3. SSO / IAM Identity Center

Wenn Ihre Organisation AWS IAM Identity Center (frueher AWS SSO) verwendet, konfigurieren Sie ein SSO-Profil in `~/.aws/config`:

```ini title="~/.aws/config"
[profile my-sso]
sso_session = my-org
sso_account_id = 123456789012
sso_role_name = BedrockAccess
region = us-east-1

[sso-session my-org]
sso_start_url = https://my-org.awsapps.com/start
sso_region = us-east-1
```

Melden Sie sich dann an und starten Sie CyberStrike:

```bash
aws sso login --profile my-sso
AWS_PROFILE=my-sso cyberstrike
```

---

### 4. STS AssumeRole (Rollenverkettung)

Wenn Sie eine Rolle in einem anderen AWS-Konto (oder eine hoeher privilegierte Rolle im selben Konto) annehmen muessen, konfigurieren Sie die Rollenverkettung in `~/.aws/config`:

```ini title="~/.aws/config"
[profile base-account]
aws_access_key_id = AKIA...
aws_secret_access_key = ...

[profile bedrock-role]
role_arn = arn:aws:iam::987654321098:role/BedrockAccessRole
source_profile = base-account
region = us-east-1
```

Verwenden Sie dann das Rollenprofil:

```bash
AWS_PROFILE=bedrock-role cyberstrike
```

Dies wird automatisch von der AWS-Credential-Provider-Kette gehandhabt — CyberStrike benoetigt keine spezielle Konfiguration.

---

### 5. Web Identity Token (OIDC)

Fuer Workloads auf **EKS (Kubernetes)**, **GitHub Actions** oder anderen OIDC-foederierten Umgebungen setzen Sie den Token-Dateipfad:

```bash
export AWS_WEB_IDENTITY_TOKEN_FILE="/var/run/secrets/eks.amazonaws.com/serviceaccount/token"
export AWS_ROLE_ARN="arn:aws:iam::123456789012:role/my-eks-role"

cyberstrike
```

Auf EKS mit IRSA (IAM Roles for Service Accounts) werden diese Umgebungsvariablen automatisch von Kubernetes gesetzt.

---

### 6. Container-Anmeldedaten (ECS / Fargate)

Bei der Ausfuehrung in **ECS**- oder **Fargate**-Tasks injiziert AWS Anmeldedaten automatisch ueber einen Metadaten-Endpunkt. CyberStrike erkennt diese Umgebungsvariablen:

- `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`
- `AWS_CONTAINER_CREDENTIALS_FULL_URI`

Keine Konfiguration erforderlich — stellen Sie nur sicher, dass die IAM-Rolle des Tasks Bedrock-Berechtigungen hat und fuehren Sie aus:

```bash
cyberstrike
```

---

### 7. EC2-Instanz-Metadaten (IMDS)

Auf **EC2-Instanzen** mit einer angehaengten IAM-Rolle werden Anmeldedaten automatisch vom Instance Metadata Service abgerufen. Keine Umgebungsvariablen oder Konfigurationsdateien erforderlich:

```bash
# Auf einer EC2-Instanz mit IAM-Rolle — einfach ausfuehren
cyberstrike
```

Stellen Sie sicher, dass die IAM-Rolle der Instanz die im Abschnitt [IAM-Berechtigungen](#iam-berechtigungen) beschriebenen Bedrock-Berechtigungen enthaelt.

<Aside variant="info">
  Wenn die Standard-Credential-Kette fehlschlaegt, faellt CyberStrike als letztes Mittel automatisch auf IMDS zurueck.
</Aside>

---

### 8. Bearer Token

Sie koennen sich mit einem Bearer Token authentifizieren. Setzen Sie es ueber eine Umgebungsvariable:

```bash
export AWS_BEARER_TOKEN_BEDROCK="your-bearer-token"
cyberstrike
```

Oder speichern Sie es ueber die TUI — fuehren Sie `/connect` aus, waehlen Sie **Amazon Bedrock** und fuegen Sie Ihr Bearer Token ein, wenn Sie dazu aufgefordert werden. Dies speichert den Token, damit Sie ihn nicht jedes Mal setzen muessen.

<Aside variant="tip">
  Bearer Token hat die **hoechste Prioritaet** — wenn gesetzt, umgeht es die gesamte AWS-Credential-Kette (Profile, Zugriffsschluessel, IAM-Rollen usw.).
</Aside>

---

### 9. Benutzerdefinierter Credential-Prozess

Wenn Sie ein benutzerdefiniertes Tool haben, das temporaere AWS-Anmeldedaten generiert (wie ein Firmen-Credential-Automat), konfigurieren Sie es in `~/.aws/config`:

```ini title="~/.aws/config"
[profile custom-creds]
credential_process = /usr/local/bin/my-credential-tool --format json
region = us-east-1
```

Das Programm muss JSON in diesem Format zurueckgeben:

```json
{
  "Version": 1,
  "AccessKeyId": "AKIA...",
  "SecretAccessKey": "...",
  "SessionToken": "...",
  "Expiration": "2025-12-31T23:59:59Z"
}
```

Verwenden Sie dann das Profil:

```bash
AWS_PROFILE=custom-creds cyberstrike
```

## Authentifizierungsprioritaet

Wenn mehrere Anmeldedaten verfuegbar sind, verwendet CyberStrike diese Prioritaetsreihenfolge:

| Prioritaet | Methode | Quelle |
|------------|---------|--------|
| 1 (hoechste) | Bearer Token | `AWS_BEARER_TOKEN_BEDROCK` Umgebungsvariable oder `/connect` in der TUI |
| 2 | AWS-Credential-Kette | `fromNodeProviderChain` loest in Standard-AWS-SDK-Reihenfolge auf: Umgebungsvariablen → Profil → SSO → Web Identity → ECS-Container → EC2 IMDS |

## IAM-Berechtigungen

Welche Authentifizierungsmethode Sie auch verwenden, die IAM-Identitaet benoetigt diese Berechtigungen:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "arn:aws:bedrock:*::foundation-model/anthropic.*"
    }
  ]
}
```

<Aside variant="tip">
  Ersetzen Sie `anthropic.*` durch einen spezifischen Modell-ARN, wenn Sie den Zugriff auf bestimmte Modelle beschraenken moechten.
</Aside>

## Regionskonfiguration

CyberStrike ermittelt die AWS-Region in dieser Reihenfolge:

| Prioritaet | Quelle | Beispiel |
|------------|--------|---------|
| 1 (hoechste) | `cyberstrike.json`-Konfiguration | `provider.amazon-bedrock.options.region` |
| 2 | Umgebungsvariable | `AWS_REGION=eu-west-1` |
| 3 (Standard) | Fest codierter Fallback | `us-east-1` |

Setzen Sie die Region in Ihrer Konfigurationsdatei:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "eu-west-1"
      }
    }
  }
}
```

Oder ueber Umgebungsvariable:

```bash
export AWS_REGION="eu-west-1"
```

## Regionenuebergreifende Inferenz

CyberStrike handhabt automatisch regionenuebergreifende Inferenz-Profilpraefixe. Basierend auf Ihrer konfigurierten Region wird das korrekte Praefix zu Modell-IDs hinzugefuegt:

| Region | Praefix | Beispiel |
|--------|---------|---------|
| US-Regionen (us-east-1, us-west-2, ...) | `us.` | `us.anthropic.claude-sonnet-4-20250514-v1:0` |
| EU-Regionen (eu-west-1, eu-central-1, ...) | `eu.` | `eu.anthropic.claude-sonnet-4-20250514-v1:0` |
| Tokio (ap-northeast-1) | `jp.` | `jp.anthropic.claude-sonnet-4-20250514-v1:0` |
| Australien (ap-southeast-2, ap-southeast-4) | `au.` | `au.anthropic.claude-sonnet-4-20250514-v1:0` |
| Andere APAC-Regionen | `apac.` | `apac.anthropic.claude-sonnet-4-20250514-v1:0` |
| Global | `global.` | `global.anthropic.claude-sonnet-4-20250514-v1:0` |

Dies geschieht automatisch — Sie muessen diese Praefixe nicht selbst hinzufuegen. Wenn eine Modell-ID bereits ein Praefix hat (z.B. aus der Modellauswahl), wird es nicht doppelt praefixiert.

## VPC-Endpunkt

Fuer privaten Netzwerkzugriff (kein Internetverkehr) konfigurieren Sie einen VPC-Endpunkt:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1",
        "endpoint": "https://bedrock-runtime.us-east-1.vpce-xxxxx.amazonaws.com"
      }
    }
  }
}
```

## Verwendung

Sobald die Authentifizierung konfiguriert ist, waehlen Sie ein Bedrock-Modell ueber `/models` in der TUI oder setzen Sie einen Standard in der Konfiguration:

```json title="cyberstrike.json"
{
  "provider": {
    "amazon-bedrock": {
      "options": {
        "region": "us-east-1"
      }
    }
  },
  "model": "amazon-bedrock/anthropic.claude-sonnet-4-20250514-v1:0"
}
```

Um Modelle waehrend einer Sitzung zu wechseln, verwenden Sie den Slash-Befehl `/model`.

## Fehlerbehebung

### "Access Denied"-Fehler

- Pruefen Sie, ob der Modellzugriff in der AWS Bedrock-Konsole aktiviert ist
- Stellen Sie sicher, dass Ihre IAM-Richtlinie `bedrock:InvokeModel` und `bedrock:InvokeModelWithResponseStream` enthaelt
- Bestaetigen Sie, dass Sie die richtige Region verwenden

### "Model not found"-Fehler

- Ueberpruefen Sie, ob die Modell-ID korrekt ist
- Pruefen Sie, ob das Modell in Ihrer Region verfuegbar ist
- Versuchen Sie eine andere Region oder aktivieren Sie regionenuebergreifende Inferenz

### "ThrottlingException"-Fehler

- Beantragen Sie eine Erhoehung des Dienstlimits ueber die AWS-Konsole
- Regionenuebergreifende Inferenz kann helfen, die Last ueber Regionen zu verteilen
- Fuer konsistenten Durchsatz erwaegen Sie AWS Bedrock-provisionierte Kapazitaet

### Bedrock-Anbieter erscheint nicht

CyberStrike zeigt den Bedrock-Anbieter nur an, wenn es gueltige Anmeldedaten erkennt. Wenn er nicht erscheint:

1. Ueberpruefen Sie, ob Ihre Anmeldedaten mit der AWS CLI funktionieren: `aws bedrock list-foundation-models --region us-east-1`
2. Stellen Sie sicher, dass mindestens eine Authentifizierungsmethode konfiguriert ist (Umgebungsvariablen, Profil, Konfiguration usw.)
3. Vergewissern Sie sich, dass der Anbieter nicht in `disabled_providers` in Ihrer `cyberstrike.json` aufgefuehrt ist
