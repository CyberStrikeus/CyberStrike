Em execucoes nao interativas (`cyberstrike run`), nao ha ninguem para responder prompts de permissao — entao qualquer ferramenta que *solicitaria* permissao e **auto-rejeitada**. Para permitir que um pipeline faca trabalho real, pre-aprove as ferramentas que ele precisa.

<img src="/docs/images/diagrams/cicd-workflow.svg" alt="Fluxo de permissao em execucao headless: uma ferramenta pre-aprovada via CYBERSTRIKE_PERMISSION ou config executa; uma que solicitaria e auto-rejeitada; resultados vao para stdout como JSON" className="my-6 mx-auto max-w-sm" />

## Pre-Aprovando Ferramentas

Nao existe flag "modo automatico". Conceda permissoes de duas formas:

**1. Variavel de ambiente `CYBERSTRIKE_PERMISSION`** — um mapa de permissao JSON (mesmo formato do campo `permission` na configuracao):

```bash
export CYBERSTRIKE_PERMISSION='{"bash":"allow","read":"allow","edit":{"reports/**":"allow"}}'
cyberstrike run "scan this codebase for security issues" --format json > report.json
```

**2. `permission` na configuracao** — faça commit de padroes seguros, negue as partes perigosas (veja [Padroes](/docs/configuration/permission-patterns)):

```json title="cyberstrike.json"
{
  "permission": {
    "read": "allow",
    "bash": { "*": "allow", "rm -rf *": "deny", "sudo *": "deny" },
    "edit": { "reports/**": "allow", ".env*": "deny" }
  }
}
```

A saida vai para stdout; use `--format json` para resultados legiveis por maquina.

## Integracao CI/CD

### GitHub Actions

```yaml title=".github/workflows/security-scan.yml"
name: Security Scan
on:
  pull_request:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm install -g @cyberstrike-io/cyberstrike@latest
      - name: Run Security Scan
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          CYBERSTRIKE_PERMISSION: '{"bash":"allow","read":"allow","edit":{"reports/**":"allow"}}'
        run: cyberstrike run "scan this codebase for security vulnerabilities" --format json > security-report.json
      - uses: actions/upload-artifact@v4
        with:
          name: security-report
          path: security-report.json
```

### GitLab CI

```yaml title=".gitlab-ci.yml"
security-scan:
  image: node:20
  variables:
    CYBERSTRIKE_PERMISSION: '{"bash":"allow","read":"allow"}'
  script:
    - npm install -g @cyberstrike-io/cyberstrike@latest
    - cyberstrike run "analyze code for vulnerabilities" --format json > report.json
  artifacts:
    paths:
      - report.json
```

## Execucoes em Lote e Agendadas

Itere sobre alvos, ou execute via cron — as mesmas regras de `CYBERSTRIKE_PERMISSION` (ou configuracao) se aplicam:

```bash title="scan-targets.sh"
#!/bin/bash
export CYBERSTRIKE_PERMISSION='{"bash":"allow"}'
while read -r target; do
  cyberstrike run "scan $target for open ports and services" --format json > "reports/${target}.json"
done < targets.txt
```

```bash
# Scan diario as 02:00
0 2 * * * CYBERSTRIKE_PERMISSION='{"bash":"allow"}' /usr/local/bin/cyberstrike run "daily security scan" >> /var/log/cyberstrike.log 2>&1
```

## Codigos de Saida e Output

`cyberstrike run` escreve resultados para stdout (`--format json` para JSON) e retorna `0` em sucesso, um codigo diferente de zero em erro ou interrupcao. Parse o JSON para descobertas:

```bash
cyberstrike run "scan target" --format json | jq '.'
```

## Consideracoes de Seguranca

- **Menor privilegio** — permita (`allow`) apenas as ferramentas que o job precisa; mantenha um `deny` explicito para `rm -rf *`, `sudo *` e caminhos de segredos.
- **Segredos** — injete chaves de API do seu armazenamento de segredos do CI, nunca faca commit delas.
- **Isolamento** — execute em um container com rede restrita quando possivel.

<Aside variant="caution">
  Sempre mantenha regras deny para comandos destrutivos ao pre-aprovar `bash` em automacao.
</Aside>
