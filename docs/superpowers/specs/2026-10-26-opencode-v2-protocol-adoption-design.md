# CyberStrike v2 API — OpenCode V2 protocol adoption

Date: 2026-10-26
Status: approved design (awaiting plan)
Scope: new package `packages/api-v2`, `packages/cyberstrike` (additive), CI, `script/`

## Intent

CyberStrike is a rebranded fork of OpenCode (`script/rebrand.ts`) whose server still speaks
OpenCode's **v1** HTTP API (Hono + zod + `describeRoute`, 146 operations, 126 paths).

`einyx/opencodex` is a native iOS/visionOS client for OpenCode. It already has a **complete v2
client path**: it probes `/global/health` (JSON ⇒ v1) then `/api/info` (⇒ v2), maps v2 payloads
through `V2Mapper`, and translates upstream v2 SSE frames through `V2EventTranslator`
(measured against upstream `v2.1.3`). Today it lands on the v1 path against CyberStrike, so the
phone runs against a protocol the fork no longer intends to keep evolving.

This project gives CyberStrike a **second HTTP surface that speaks upstream's v2 wire contract
exactly**, implemented over CyberStrike's existing domain, so that:

- the phone speaks v2 against CyberStrike with no app change,
- `einyx/opencodex/scripts/v2_contract_check.py` becomes a **CI gate** instead of an external
  script nobody runs,
- future upstream protocol changes are adopted by bumping a pinned npm dependency, not by
  hand-reimplementing shapes.

## Decisions (human partner)

1. **D1 = protocol-layer adoption.** Adopt upstream's v2 *contract and machinery*
   (`@opencode/protocol`, `@opencode/schema`, `@opencode/client`) and implement the surface over
   CyberStrike's domain. Explicitly **not** a full upstream monorepo rebase, and **not** a
   hand-rolled v2 API.
2. **The contract script is the spec.** `scripts/v2_contract_check.py` (~50 assertions) is the
   acceptance criterion.
3. **No phone-side changes in this project.** opencodex's v2 path already exists and is
   sufficient; CyberStrike-specific *views* on the phone are a separate project.
4. **Package structure: inverted.** `packages/api-v2` owns only the contract (endpoint
   definitions, projections, event mapping). The glue that calls CyberStrike's internals —
   handlers, middleware, the listener — lives in `packages/cyberstrike`, which already depends
   on `api-v2`. No circular workspace imports; `api-v2` stays domain-agnostic and independently
   testable.
5. **The terminal must work in phase 1.** The v2 surface must support a live PTY WebSocket, so
   the phone's terminal works against CyberStrike. See *Terminal / WebSocket*.

## Goals

- A v2 surface whose `openapi.json` is upstream's `openapi.json` plus CyberStrike's fork groups,
  generated by upstream's own codegen.
- Every endpoint the contract gate and the phone exercise implemented faithfully.
- The v1 surface keeps working, untouched, for `packages/app`, `packages/enterprise`,
  `packages/slack`, and the browser extension.
- The fork's pentest domain reachable from v2 (phase 2).

## Non-goals

- Moving the web UI, plugin contract, Slack app, or hackbrowser extension to v2.
- Migrating CyberStrike's database to upstream's `session_v2` / `session_message` tables.
- Merging upstream's `packages/core` (the rebase). Not doing it is the point of this design.
- Reimplementing upstream's `packages/core` domain. CyberStrike's domain stays authoritative.
- Supporting upstream-only features CyberStrike has no equivalent for (see *Surface scope*).

## Anti-goals

- **No v1 shapes on the v2 surface.** The gate asserts `/global/health` is not 200-JSON,
  `/session/status` is not a JSON map, `/session/:id/todo` is 404, `/project/current` is absent.
  The v2 listener therefore mounts **only** v2 routes.
- **No silent degradation.** A v2 endpoint that cannot be honoured returns a real HTTP 503, never
  a v1-shaped 200.
- **No forked copy of upstream's protocol package.** Depend on the published npm packages and
  import upstream's group definitions unmodified. Upstream is MIT; CyberStrike is AGPL-3.0-only —
  MIT dependencies are compatible.
- **No circular workspace imports.**

## Constraints

| Constraint | Consequence |
|---|---|
| `makeApiFromGroup` is **not exported** by `@opencode/protocol`; `makeApi`/`makeDefaultApi` accept no extra groups | CyberStrike re-assembles the `HttpApi` itself: copy the `.add(...)` chain from upstream's `packages/protocol/src/api.ts` and append fork groups. Importing upstream's groups from `@opencode/protocol/groups/*` keeps them byte-identical. |
| `HttpApiBuilder` requires a handler for **every** endpoint in the `HttpApi` | Upstream groups with no CyberStrike equivalent still need a handler. |
| Upstream's handlers call `@opencode/core` services, which CyberStrike does not use | **Every** upstream endpoint gets a CyberStrike handler. Upstream's handler layer is not reusable. |
| Upstream's server layer is bound to upstream's `Api` instance | CyberStrike builds its own `HttpApiBuilder.layer(...)` + middleware layers, mirroring upstream's `packages/server/src/routes.ts`. |
| CyberStrike's v1 DB uses `session`/`message`/`part`/`todo`; upstream v2 uses `session_v2`/`session_message` | CyberStrike keeps its own schema. The v2 surface reads the same tables through the same domain modules. No data migration. |
| Effect 4's `HttpEffect.toWebHandlerWith` cannot upgrade a request (`"Not an upgradeable ServerRequest"`) | The PTY WebSocket cannot be served through the Effect web handler. See *Terminal / WebSocket*. |
| A handler's error channel is fixed to the endpoint's **declared** errors; most upstream groups do not declare `ServiceUnavailableError` | Stubs return a raw `HttpServerResponse` 503 (allowed in the success channel) rather than `Effect.fail`. Upstream's group definitions stay unmodified; the 503 is not in the OpenAPI's declared responses, and our docs state it. |
| The contract script probes one base URL | The v2 surface must be reachable as a **single base URL** with no v1 routes on it ⇒ separate listener. |

## Architecture

### Two packages, one direction

```
packages/api-v2/                       @cyberstrike-io/api-v2   (contract only)
  src/
    api.ts                             HttpApi assembly: upstream's 31 groups
    projection/                        v1 domain shapes -> v2 wire shapes (pure functions)
      session.ts  message.ts  permission.ts  form.ts
    events.ts                          v1 bus event -> v2 frame mapping (pure)
  script/generate-openapi.ts           writes openapi.json (mirrors upstream's script)

packages/cyberstrike/src/api-v2/       (glue — the only place that knows the domain)
  handlers/<group>.ts                  HttpApiBuilder handlers, one file per group
  handlers.ts                          merges every group handler
  middleware.ts                        authorization + schema-error + location layers
  server.ts                            Bun.serve: PTY upgrade + Effect web handler
```

`packages/api-v2` never imports `packages/cyberstrike`. `packages/cyberstrike` imports
`api-v2` for the `Api` and the projections. Handlers live beside the domain they call, so
they import `../../session` directly — **no port interfaces and no adapter layer**: a port
layer would be ceremony when both sides are in the same package. The projections are the only
cross-boundary code, and they are pure functions over plain data, so a drift between their
input types and CyberStrike's domain types is a compile error at the call site.

### Two listeners, one process, one database

```
cyberstrike serve                 # v1 listener :4096  (unchanged behaviour)
cyberstrike serve --api v2        # v2 listener :4198  (new; mounts ONLY v2 routes)
```

Both run in the same process against the same domain modules and the same SQLite handle
(WAL + `busy_timeout=5000` already set in `packages/cyberstrike/src/storage/db.ts`), so there is
no cross-process SQLite contention. The v2 listener mounts no v1 route group, which is what
satisfies the gate's negative assertions.

Flag-gated and **off by default**: existing deployments are unaffected. CyberStrike's v1 server
is `Bun.serve({ fetch: App().fetch, websocket })`; the v2 listener is a second `Bun.serve` in the
same process with the same shape.

### Terminal / WebSocket

`pty.connect` is a WebSocket upgrade, and Effect 4's web-handler route cannot upgrade a request.

**Approach: upgrade in front of Effect.** The v2 listener's `Bun.serve` handles the PTY connect
path natively, exactly as the v1 server does today, and delegates everything else to the Effect
web handler:

```ts
Bun.serve({
  fetch(req, server) {
    if (isPtyConnect(req)) return upgradePty(req, server)   // Bun native
    return effectHandler(req)                                 // Effect web handler
  },
  websocket: { open(ws) { Pty.connect(ws.data.id, ws) }, ... },
})
```

CyberStrike's existing `Pty.connect(id, ws, cursor?)` is reused **verbatim**: its `Socket` type is
structural (`readyState`, `send`, `close`) and Bun's `ServerWebSocket` satisfies it as-is, so no
socket adapter is needed. The v1 route's behaviour (buffer replay from a cursor, control frames,
`Pty.write`, `Pty.resize`) carries over unchanged.

The Effect-side `pty.connect` endpoint still exists (upstream's group defines it, and the OpenAPI
+ generated client reference it), but its handler returns 503 — the real upgrade happens in front
of Effect, so the Effect handler is unreachable. This is documented, not hidden.

`@effect/platform-bun` is **not** used: it would add a runtime dependency and a less battle-tested
Effect platform to save an adapter that the structural `Socket` type already makes unnecessary.

### Handler shape

Every handler bridges CyberStrike's promise-based domain into Effect and reshapes the result:

```ts
export const SessionHandler = HttpApiBuilder.group(Api, "server.session", (handlers) =>
  handlers.handle("session.list", Effect.fn(function* (ctx) {
    const sessions = yield* Effect.promise(() => sessions.list({ directory: ctx.query.location?.directory }))
    return { data: sessions.map(projectSession) }   // v1 Info -> v2 Session.Info
  })),
)
```

`Effect.promise` bridges CyberStrike's promise domain. Errors map to upstream's
`Schema.TaggedError` classes (`SessionNotFoundError` 404, `InvalidRequestError` 400,
`ConflictError` / `SessionBusyError` 409, `UnauthorizedError` 401) so the generated client and
the gate see upstream's error envelope.

### Location / directory scoping

Accepted on the v2 surface, all equivalent:

- `?location[directory]=…` (upstream's deepObject form — what the gate and the phone use)
- `?directory=…` (CyberStrike v1's form)
- `x-opencode-directory: …` (upstream's header)
- `x-cyberstrike-directory: …` (CyberStrike v1's header)

Accepting all four is cheap and removes a silent "wrong directory" failure mode.

### Auth

The v2 listener reuses CyberStrike's existing Basic-auth middleware verbatim: username
`CYBERSTRIKE_SERVER_USERNAME ?? "cyberstrike"`, password `CYBERSTRIKE_SERVER_PASSWORD`, loopback
requests trusted without a password.

Consequences, stated plainly:

- The contract script's default `V2_USER=opencode` **must be overridden** to `cyberstrike` in CI.
- Because the gate runs on loopback, it does **not** exercise the auth path. That is a known
  limitation of the gate, not a claim that auth is verified. Auth stays covered by CyberStrike's
  existing v1 tests.

### Projections (the hard part)

Upstream's v2 message model is not a rename of v1. Upstream ships the v1 decoders
(`@opencode/schema/v1/session`) **and** the transform used by its own data migration
(`packages/core/src/database/v1-migration.bun.ts` → `transformSession`). CyberStrike uses both as
the reference for `packages/api-v2/src/projection/message.ts`:

| v1 (CyberStrike) | v2 (upstream wire) |
|---|---|
| `GET /session/:id/message` → `[{info, parts[]}]` | `{data: SessionMessageInfo[], cursor}` — flat, `type` discriminator, inline `content[]` |
| part `type:"tool"`, `{callID, tool, state}` | content `{id, name, state:{status,input,content,error}, time}` |
| part `type:"text"` + delta events | `session.text.started/delta/ended` with `assistantMessageID` + `ordinal` |
| assistant `{providerID, modelID, error:{name,data}, finish}` | `model:{id,providerID,variant?}`, `error:{type,message}`, `finish:"stop"\|"length"\|…` |
| `Session.Info {directory, permission}` | `Session.Info {location:{directory}, permissions}` |
| `POST /session/:id/message {parts:[…]}` | `POST /api/session/:id/prompt {text, files?, agents?, skills?}` — returns the **admission**, not the reply |
| `POST /session/:id/abort` | `POST /api/session/:id/interrupt?resume=` → `{interrupted: bool}` |
| `Permission {type, pattern}` + reply `{reply}` | `Permission.Request {id:"per_…", action, resources[]}` + reply `{decision}` |
| `Question {question, header, options[]}` | `Form` (typed fields, `pending/answered/cancelled` state) — reply `{answer}` → 204 |
| `GET /file?path&directory` → bare array | `GET /api/fs/list?location[directory]` → `{location, data}` |
| `GET /file/content` → text | `GET /api/fs/read/*` → raw bytes |
| errors `{name, data:{message}}` | `{_tag:"SessionNotFoundError", message}` |
| `PATCH` → 200 + body | `PATCH` → **204, empty body** |

CyberStrike's extra v1 part types (`json_schema`, `symbol`, `resource`) have no upstream
counterpart; the projection maps them to v2 `text` content with the original payload preserved in
metadata, recorded as a known gap.

The projection is the highest-risk piece of the work and gets a **spike** before the slice order
is fixed (see *Risks*).

### Event stream

The v2 surface emits upstream's flat frame `{id?, type, data}`. The phone's `V2EventTranslator`
reads exactly these types:

`server.connected`, `session.status`, `session.idle`, `session.created`, `session.renamed`,
`session.metadata.updated`, `session.deleted`, `session.text.started`, `session.text.delta`,
`session.text.ended`, `session.reasoning.ended`, `session.message.content.updated`,
`permission.asked`, `permission.replied`, `form.created`, `form.replied`, `form.cancelled`,
`session.execution.failed`.

CyberStrike's bus speaks `{type, properties}` with ~40 v1 event names.
`packages/api-v2/src/events.ts` maps the v1 names onto this list. Anything unmapped is dropped
rather than emitted under a wrong name — a dropped event is a missing live update, a wrong-named
event is a corrupted one.

### Fork groups (phase 2)

`vulnerability`, `request`, `observation`, `coverage-note`, `web-credential`, `methodology`,
`hackbrowser`, `ingest`. Each becomes a new `HttpApiGroup` in `packages/api-v2/src/groups/`,
appended to the `HttpApi` assembly, over tables that already exist in CyberStrike's schema (no
DB migration — only the HTTP surface is new).

**Phase 1 ships no fork groups** — `packages/api-v2/src/groups/` does not exist yet. Phase 2 adds
the groups and regenerates `openapi.json` + the generated client. The OpenAPI drift check
enforces consistency, not immutability.

## Acceptance

1. **`script/v2-contract-check.py`** — vendored from `einyx/opencodex` into CyberStrike's repo
   (Apache-2.0 → AGPL-compatible; attribution kept). Runs against a booted v2 server in CI with
   `V2_USER=cyberstrike`. All assertions pass.
   *The `V2_ALLOW_PROMPT=1` variant (prompt admission, fork, revert) is **deferred** to a
   follow-up: it needs a provider key and a named model, and this repo has no nightly workflow
   today. Until then, prompt/fork/revert coverage is untested at merge time.*
2. **`openapi.json` drift check** — `bun run generate` produces no diff (mirrors upstream's
   `check:generated`).
3. **Typecheck** — `bun run typecheck` across the workspace, including `packages/api-v2`.
   This is also what catches upstream drift: if a pinned upstream package changes its group
   assembly, our copied chain stops typechecking.
4. **Existing v1 surface unaffected** — the v1 contract (146 operations) is unchanged; the web UI
   build and the existing server tests still pass.
5. **Phone smoke test — manual, pre-merge, by the requester.** Point opencodex at the v2
   listener: it must detect v2 (the probe falls through `/global/health` to `/api/info`), render a
   live streamed reply, answer a permission prompt, and open a terminal session. **Not** a CI
   gate — it needs a device and a model key.

## Risks

| Risk | Mitigation |
|---|---|
| **Projection bugs on edge-case message shapes** (tool errors, compaction, subagent) | Spike first: prototype `transformSession`'s mapping against CyberStrike's actual rows before fixing the slice order. Unit tests per projection, mirroring upstream's `v1-migration.test.ts` fixtures. |
| Upstream changes the group set / middleware wiring → our copied assembly chain type-errors | Pin `@opencode/protocol` exactly; the CI typecheck fails loudly on drift; the fix is to copy the new chain. |
| Event mapping gaps → silent loss of live updates | One case per event type in one file; the phone smoke test covers text streaming, tool calls, permission, form, terminal. |
| v1 and v2 surfaces drift apart over time | v1 is frozen by this project; v2 is the evolving surface. |
| The 503 stub shape is not in the OpenAPI | Upstream's group definitions stay unmodified by choice. Documented in this file and in the v2 README. |
| Two listeners → two auth paths | Reuse CyberStrike's existing Basic-auth middleware verbatim. |

## Fixes included regardless of scope

Found during scoping; each is small and independently valuable:

1. **Unify the SDK trees.** `packages/sdk/js/src/gen/` (78 endpoints, stale) and `src/v2/gen/`
   (146 endpoints, current) coexist. `packages/plugin` and
   `packages/cyberstrike/src/plugin/index.ts` import the **stale** tree, so plugins cannot call
   `/bolt`, `/skill`, `/methodology`, `/question`, `/permission`, `/session/:id/web/*`, or
   `/session/ingest` today. **Non-destructive fix:** regenerate `src/gen` from the current server
   so both trees are identical, keep the published `./v2` export path (removing it would break
   external consumers of the npm package), and repoint plugins at `./v2`.
   *Note: `src/v2/` is **not** upstream v2 — it is v1 codegen round 2, a trap for anyone planning
   this migration.*
2. **Remove the layering inversion.** `src/tool/task.ts` and `src/tool/web-get-request-detail.ts`
   import helpers (`renderAccessContextLines`, `resolveVisitedBy`) out of the 2,170-line
   `src/server/routes/session.ts`. Move them into `src/session/`.
3. **Export the two missing tables.** `RequestObservationTable` and `CoverageNoteTable` are not
   re-exported from `src/storage/schema.ts`, so they escape `Database.reconcile()`'s column-repair
   loop and the Drizzle schema object.

## Explicitly out of scope

- Web UI → v2 (131 SDK call sites, 6 raw fetches, a 40-event reducer).
- Plugin contract → v2 (`packages/plugin` types the client as the exact v1 client shape; every
  third-party plugin breaks at compile time).
- `packages/hackbrowser`'s 4 hardcoded v1 paths (`/session/ingest`, `/session/:id/web/credentials`).
- DB schema → upstream's `session_v2` / `session_message`.
- Upstream `packages/core` merge.
- Phone-side CyberStrike-specific views (opencodex feature work).
